# The effect pipeline model

> Companion to `docs/effect-pipeline.svg` (generated by
> `docs/diagrams/gen-effect-pipeline.py`). Describes a proposed refactor of the
> renderer around one rule: **every effect is a function from an input image to
> an output image, and the FX stack *is* the order.**

This is a design document, not a shipped change. No backwards compatibility is
required, so the current `*Order` integer plumbing can be deleted rather than
kept alongside the new model.

---

## 1. The contract

```
Effectᵢ : (input: Texture, params: EffectParams, aux: AuxTextures) -> output: Texture
```

- `input` is the image produced by the effect above it in the stack.
- `output` is the image the next effect reads.
- `aux` is anything the effect needs but does not transform in place: the camera
  colour texture, the alpha matte, a decoded video frame, a pose buffer.
- The stack starts from a **seed** image (camera × matte composited over the
  background) and ends at the drawable that gets presented.

Order is no longer computed per pixel from integer comparisons. Order is the
array position. Two effects that both want to write the same stage is a bug the
type system can catch, not a sentinel value (`UInt32.max`) that silently means
"not present".

## 2. Categories

Every effect falls into exactly one category. The category decides *how* the
renderer realizes the node, which is the only thing that affects cost.

| Category | What it does | Realization | Members |
|---|---|---|---|
| **seed** | produces the starting image | 1 fused pass | subject-over-background composite |
| **transform** | pixel-local remap/blend of the image | **fusable** into an adjacent pass | Gradient Overlay, Video Fill, Liquid Distortion, (future colour grade / vignette / grain) |
| **composite** | draws new geometry on top | own pass | Skeleton, Lines, Particles, Clap Explosions |
| **feedback** | reads previous frames | own pass + ring buffer | Historical Trail, Line Sampler |
| **gather** | re-samples the image by coordinate | own pass (read snapshot → write) | Kaleidoscope |

The category is not decorative. It is the scheduler's contract:

- a run of adjacent **transform** nodes compiles into **one** compute dispatch,
  because they are all `f(gid) -> colour` with no neighbour reads;
- a **composite** node must be its own pass (it rasterizes primitives);
- a **feedback** node must be its own pass and owns history textures;
- a **gather** node must be its own pass and cannot read the texture it writes.

## 3. Why fusion is the whole ballgame

Naively, one pass per effect is the cleanest possible model — and the most
expensive. Cost is dominated by bandwidth, not ALU:

```
bandwidth ≈ passes × resolution × (read + write)
```

At 1080p (`1920×1080`, BGRA8) one full pass moves ≈ 16.6 MB. At 60 fps that is
≈ 1 GB/s. The M1 Pro has on the order of 200 GB/s, so a handful of passes is
nothing — but the projector output can be **4K** (`3840×2160`, 4× the pixels),
and the matting model plus video decode are already competing for that budget.

Today Gradient + Video + Liquid are *already* fused into the base/subject
shader; their relative order is expressed by `gradientOrder`, `videoOrder`,
`liquidOrder` and `processingLimitOrder`, compared per pixel. If the refactor
simply gave each of them its own pass, a preset using all three would go from 1
pass to 4. Fusion is what keeps the uniform model affordable.

So the rule is: **the model is uniform; the scheduler fuses.** A transform node
declares itself fusable and the scheduler merges maximal adjacent runs of
transform nodes into a single dispatch.

## 4. Buffers

- **A / B ping-pong** — two full-resolution colour textures. A pass reads one,
  writes the other, then they swap. This removes the "cannot read what you
  write" hazard for gather and transform nodes without a separate blit.
- **ring buffers** — owned by feedback nodes (trail snapshots, line-sampler
  strips). Unchanged from today.
- **aux textures** — camera colour, alpha matte, current video frame, pose
  buffers. Read-only inputs; not part of the colour chain.

The ping-pong pair replaces today's "every pass reads and writes the same
drawable" pattern, where each pass does a same-pixel `read → modify → write`.
That pattern is safe but only because every existing pass happens to touch its
own pixel, which is exactly the constraint a gather node breaks.

## 5. Ordering: today vs proposed

**Correction to an earlier draft of this doc.** The `*Order` integers are *not*
a second source of truth. `AppController.syncEffects()` sets
`renderer.effectOrder = enabledEffects`, and every integer the shaders consume is
**derived** from that one array at draw time:

```swift
private func effectOrderValue(_ effect: EffectKind) -> UInt32 {
    effectOrder.firstIndex(of: effect).map { UInt32($0) } ?? UInt32.max
}
```

So ordering already has a single source of truth. The integers are a *mechanical
encoding* of the array position, not a parallel representation that can drift.
This matters: the refactor below is **not** a correctness fix. Order is already
correct. The refactor is purely about **structure and change-cost**.

**Today.** `draw(in:)` is a fixed sequence of hardcoded call sites
(`encodePass(basePipeline…)`, the trail loop, `encodePass(subjectPipeline…)`,
`encodePoseOverlays`, `encodeClapExplosions`, `encodeLineSampler`,
`encodeKaleidoscope`). Which effects are fused vs. which are passes is implicit
in the code's shape. Adding an effect means touching `EffectKind`,
`EffectPreset`, `AppController` (published props + `syncEffects` + preset +
randomize), `ContentView`, the shader, `ShaderParams`, and a call site in
`draw()`.

**Proposed.** The same execution, but the sequence is *built from a list*:

```swift
func render() {
    var target = seedStage()
    for node in stack {          // stack order == processing order
        node.input = target
        node.output = nextBuffer()
        node.encode(into: commandBuffer)
        target = node.output
    }
    present(target)
}
```

The win is that adding an effect becomes "append a stage" instead of editing a
dozen places. The *behaviour*, and therefore the cost, should be identical.

## 6. What changes (no back-compat)

- **`MetalRenderer`** — replace per-effect `*Enabled` / `*Order` properties with
  a `[EffectStage]` built from the preset each time the stack changes. Delete
  `effectOrderValue` and the `processingLimitOrder` plumbing from the shaders.
- **`basePass` / `subjectPass` / `trailPass`** — split into: a seed composite
  kernel, and a fused transform kernel that takes an ordered *list* of transform
  ops as a buffer (or one specialised kernel per transform, fused by the
  scheduler choosing which entry point to bind).
- **`EffectPreset`** — drop every `... ?` optional field and the legacy
  `CodingKeys`. One current schema. Presets from older builds no longer load;
  that is the accepted trade.
- **`AppController`** — `activeEffects` becomes the pipeline; `syncEffects`
  rebuilds stages instead of mirroring ~50 individual properties onto the
  renderer.
- **`EffectKind`** — gains `category` and `isFusableTransform`, which is the
  only metadata the scheduler needs.

## 7. Risks / what could go wrong

The overriding risk is **performance**: you do not want the render path slower.
Break it down by what actually changes:

| Refactor flavour | Pass count change | Perf |
|---|---|---|
| Parity-preserving (transforms stay fused) | 0 | unchanged |
| Uniform one-pass-per-effect | +2…+3 full-res passes | **slower** |

With trails maxed the frame is already ~20 passes (16 of them `trailPass`), so
+2 passes is roughly **+10 %**, and at 4K that +10 % is on 4× the pixels.

1. **Splitting the fused transforms is the only real slowdown.** Gradient +
   Video + Liquid currently cost *zero* extra passes. Any refactor that gives
   them their own passes is a straight regression. If you refactor, the fusion
   must be preserved — which means the scheduler is not optional.
2. **Shader count and compile time.** The Metal library is compiled from source
   at launch (~35 KB today). Splitting kernels grows that string.
3. **Respecializing fusions.** "Fuse adjacent transforms" means the dispatch
   shape depends on *which* transforms are adjacent. Either one branchy kernel
   with an op-list buffer (fixed entry points, runtime branching) or precompiled
   permutations (fast, combinatorial). Pick one deliberately.
4. **`processingLimitOrder` is load-bearing.** It is how the Line Sampler gets
   the pre-trail image. Re-expressing it as "sample the ring snapshot at my
   position" is natural in the new model but is real behaviour to preserve.
5. **"No back-compat" buries saved looks.** Dropping the `... ?` optional fields
   means every existing preset silently stops loading. Deliberate, or a side
   effect — decide.

## 8. Cost summary

| | today | uniform 1-pass-per-FX | scheduled fusion |
|---|---|---|---|
| 1080p, 3 transforms | 1 pass | 4 passes | 1 pass |
| 4K, full stack | ~20 passes | ~22–23 passes | ~20 passes |

## 9. Recommendation

Because ordering is **already** single-source (section 5), the refactor buys
structure, not correctness, and its only real downside is perf. So:

- **Do now (zero risk):** add `EffectKind.category` and
  `isFusableTransform` as pure metadata, and keep the diagram + this doc as the
  spec. Optionally use `category` to group the FX rows in the UI.
- **Do not do now:** restructure the render hot path. There is no ordering bug
  to fix, and the pass-parity requirement makes the refactor's only guarantee
  "…if the scheduler is right".
- **Revisit when** adding an effect becomes the bottleneck, or when you need a
  genuinely new execution shape (e.g. several more transforms, where fusion
  stops being a detail and starts being the design).

If it is done later, it must be **staged and gated**:

1. Compute a `PipelinePlan` (list of passes + texture assignments) *without*
   changing execution. Assert it equals today's sequence.
2. Route `draw()` through the plan. Compare `renderMS` (already surfaced in the
   metrics row via `PerformanceMonitor`) before/after at 1080p **and** 4K.
3. Delete the integers only once the plan provably matches.

**Decision rule:** if you are not willing to verify `renderMS` at both 1080p and
4K after each slice, do not refactor — because "is it slower?" becomes a vibe
instead of a measurement.

## 10. What shipped (the UI alignment)

The renderer was **not** restructured. Instead the UI was made to match what the
renderer actually does, and the one cheap gap in the renderer was closed.

### 10.1 Two stages, shown in the stack

`EffectKind.pipelineStage` declares which half of the pipeline an effect runs in:

- **Image pipeline** — Gradient Overlay, Video Fill, Liquid Distortion,
  Historical Trail, Skeleton, Lines, Particles. Composited with the frame;
  reorder freely.
- **Post** — Clap Explosions, Kaleidoscope, Line Sampler. Runs on the finished
  frame; the boundary is fixed.

The FX stack now renders a **labelled divider** at that boundary, and the up/down
arrows are disabled across it. `AppController.canMove(_:by:)` is the single check
the buttons, the help text and `moveEffect` all share, so the UI cannot offer a
move the renderer would ignore. `addEffect`, preset apply and randomize all pass
through `normalizedEffectOrder`, a stable partition that puts image effects
before post effects — relative order inside a stage is preserved, so it never
changes a look.

### 10.2 The one renderer fix

Skeleton / Lines / Particles were drawn in a fixed order (skeleton → lines →
particles) regardless of the stack, so moving them did nothing. `encodePoseOverlays`
now sorts the three by `effectOrderValue`, so their stack position is honored —
which is what the UI was already promising.

### 10.3 Honored vs not (the honest table)

| Reorder | Honored | Mechanism |
|---|---|---|
| Gradient ⇄ Video Fill | ✅ | `effectedColor` compares `gradientOrder` / `videoOrder` |
| Colour ⇄ Historical Trail | ✅ | `effectedTrailColor` decides if trail layers get coloured |
| Colour ⇄ Lines / Particles | ✅ | `effectedLineColor` / `effectedParticleColor` |
| Trail ⇄ Skeleton / Lines / Particles | ✅ | upstream signal capture in `shouldCaptureSignal` |
| Skeleton ⇄ Lines ⇄ Particles | ✅ (fixed this change) | overlay draw order now follows the stack |
| Liquid ⇄ Trail / Particles | ✅ partial | mask capture + `liquidAffectsParticles` |
| Kaleidoscope ⇄ Explosions / Line Sampler | ✅ | slot A / B / C |
| Liquid ⇄ Gradient / Video | ❌ | the warp is always applied at sampling time |
| Kaleidoscope above the image pipeline | ❌ | it is a gather over the composited frame |
| Explosions ⇄ Line Sampler | ❌ | explosions always composite before the sampler |
| Any image effect ⇄ any post effect | ❌ | fixed boundary, shown as the divider |

The ✅ rows are what the arrows offer. The ❌ rows are why: two of them are
*structural* (a gather cannot run before the image exists; explosions must feed
the sampler), and one is a *consequence* (Liquid is a coordinate warp applied
when the frame is sampled, so it has no position relative to the colour blends).
